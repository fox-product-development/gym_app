## 1. Registration — Approved Email Invite System

### Decision

Invite-only registration via a pre-approved email list. Not open to public registration.

### How it works

- Admin maintains a list of approved email addresses in the approved_emails table
- Registration form: Email, Username, Password
- Checks on submit: (1) email on approved list and not used, (2) username available
- On success: account created, approved_emails.used set to TRUE

### Admin management

- Settings screen (admin only) shows approved emails section
- Add email via text input — written to approved_emails table immediately
- Registered entries show "Registered" badge, unused show "Pending"
- Only pending emails can be deleted from the list

### Database

```sql
CREATE TABLE approved_emails (
  id       SERIAL PRIMARY KEY,
  email    TEXT NOT NULL UNIQUE,
  used     BOOLEAN NOT NULL DEFAULT FALSE,
  added_at TIMESTAMP DEFAULT NOW()
);
```

## 3. Onboarding Flow

Shown once after registration (goal_size is null check in \_layout.tsx).
Also accessible via Settings → Goals → warning modal → Redefine goals.

### Steps

1. Goal star ratings (Size, Strength, Definition, General fitness — 1–5 each)
2. Training level (New / Amateur / Serious / Professional)
3. Weekly sessions (pre-filled suggestion based on level, adjustable +/−)
4. Free text description (optional)

### Mode parameter

- Default (no param): navigates to /(tabs) on completion
- ?mode=redefine: prepopulates existing values, navigates back to settings on save, shows "Update your goals" title and "Save changes" button

### Warning modal (redefine mode)

Appears before navigating to onboarding from settings:
"Changing your goals will recalculate your training cycle. Your current block will complete as planned before any changes take effect."
→ Continue or Cancel

## 4. Personalised Phase Cycle

### Decision

phase_cycle is a JSONB array stored per user defining their AI-generated training sequence.

### Example values

High definition focus:

```json
[
  { "phase": "anatomical_adaptation", "blocks": 2 },
  { "phase": "muscle_definition", "blocks": 2 },
  { "phase": "anatomical_adaptation", "blocks": 1 },
  { "phase": "hypertrophy", "blocks": 1 },
  { "phase": "muscle_definition", "blocks": 2 }
]
```

### Behaviour

- Generated by AI at registration based on goal ratings (not yet implemented — currently set manually)
- Updated immediately when goals are redefined
- Cron reads phase_cycle per user to determine next phase (falls back to fixed 4-phase rotation if null)
- Takes effect naturally at next block generation

## 5. Gym Configuration

### Decision

Gyms are user-scoped. Each user defines their own gyms independently. No shared library.

### Database

```sql
CREATE TABLE gyms (
  id         SERIAL PRIMARY KEY,
  user_id    INTEGER REFERENCES users(id),
  gym_name   TEXT NOT NULL,
  is_default BOOLEAN NOT NULL DEFAULT FALSE,
  created_at TIMESTAMP DEFAULT NOW()
);
```

### Default gym behaviour

- Default gym drives block generation
- Changing default takes effect at next block generation
- Only one gym can be default at a time

### Current data

- Work Gym (id=1, is_default=true)
- Home Gym (id=2, is_default=false)

## 6. Equipment Configuration

### Equipment types

| Type      | Description                            | Weight entry                |
| --------- | -------------------------------------- | --------------------------- |
| loadable  | Barbell, EZ bar, loadable dumbbells    | Unladen weight + plate pool |
| fixed     | Pre-weighted dumbbells, fixed barbells | Increment value             |
| machine   | Cable stack, leg press, chest press    | Increment value             |
| apparatus | Bench, rack, pull-up bar               | No weight                   |

### Plates

Pooled per gym, not per piece of equipment. Quantity editable via +/− inline controls with save bar.

### Database

```sql
CREATE TABLE equipment (
  id                SERIAL PRIMARY KEY,
  user_id           INTEGER REFERENCES users(id),
  gym_id            INTEGER REFERENCES gyms(id),
  equipment_name    TEXT NOT NULL,
  type              TEXT NOT NULL CHECK (type IN ('loadable','fixed','machine','apparatus')),
  unladen_weight_kg NUMERIC(5,2),
  increment_kg      NUMERIC(5,2),
  created_at        TIMESTAMP DEFAULT NOW()
);

CREATE TABLE plates (
  id         SERIAL PRIMARY KEY,
  user_id    INTEGER REFERENCES users(id),
  gym_id     INTEGER REFERENCES gyms(id),
  weight_kg  NUMERIC(5,3) NOT NULL,
  quantity   INTEGER NOT NULL DEFAULT 0,
  created_at TIMESTAMP DEFAULT NOW()
);
```

## 7. Exercise Library

### gym_id migration

exercises table now has gym_id FK alongside the existing gym TEXT field.

- Work exercises: gym_id = 1
- Home exercises: gym_id = 2
- buildGymCSV queries by gym_id with TEXT fallback for compatibility

### Active flag

exercises.active BOOLEAN (default true). Checkbox in gym settings toggles this. Inactive exercises are excluded from AI planning.

### Add exercise flow

1. Enter exercise name
2. AI lookup via /ai/exercise-metadata — returns muscles_primary, muscles_secondary, type, sub_component, emg_score
3. User reviews pre-filled metadata
4. Confirm → saved to exercises table

### Suggest exercises

- Button on exercises tab → calls /ai/suggest-exercises with gym_id
- AI checks equipment list, excludes existing exercises, suggests 20–30 appropriate exercises
- Results shown in modal grouped by Compound/Isolation then muscle
- All selected by default, user unchecks unwanted
- Add selected → batch create

### Delete exercise — three step flow

1. Kebab → Remove
2. Modal 1: warning about permanent deletion → Continue or Cancel
3. Modal 2: final confirmation → "Delete exercise and all data" (red) or Cancel
4. Deletes exercise row, all logged_sets for that exercise, all one_rep_max_history for that exercise

## 11. Sunday Report Redesign

### Philosophy

Causal storytelling, not parallel category summaries. The agent reasons across all data to find connections between diet, mood, energy, cardio, and session performance.

### Structure

1. **Headline** — one sentence capturing the character of the week
2. **Looking back** — connected narrative explaining what happened and why across all data sources
3. **Stop / Start / Continue** — 2–3 specific evidence-based actions per section

### Data sources

- Sessions + logged sets (last 4 weeks)
- Progressive overload flags
- 1RM history
- Body composition (last 4 weeks)
- Diet logs (last 2 weeks)
- Mood and energy logs (last 2 weeks)
- Cardio logs (last 2 weeks)
- User goal profile and agent tone

### Agent tone

Report language adapts to user's agent_tone setting:

- motivational — encouraging, celebratory
- neutral — factual, no fluff
- coaching — explains the why
- drill_sergeant — direct, high expectations

### Email delivery

- Report stored in weekly_feedback table (existing)
- Additionally sent via Resend to user.email
- From: coach@activitycoach.co.uk
- Styled HTML email matching app dark theme

### Manual trigger

POST /report/generate

- No body: generates for current week if no report exists, returns {status: "up_to_date"} if one exists
- Frontend always sends week_start_date: Sunday = today, any other day = last Sunday
- With date: deletes existing report for that week and regenerates

## 13. Session Gym Swap

### Updated behaviour

StartSessionModal now loads user's gym list dynamically.

- One gym defined: no swap option
- Two gyms: same as original behaviour (effectively a toggle)
- Three+ gyms: list of all non-default gyms as secondary buttons

### Flow

1. Default gym button → starts session immediately (no regeneration)
2. Other gym button → confirmation step → regenerates exercises for that gym

### Known limitation (backlog)

generateHomeSession is still called regardless of which non-default gym is selected. Backend needs updating to pass the selected gym_id and regenerate appropriately for any gym, not just home.
